INSIGHT architecture

Accepted target architecture, runtime trust boundaries, Research Case state machine, MCP contract, domain model, storage behavior, and current repository implementation—kept separate so planned capabilities are never presented as working software.

Evidence snapshot: 2026-08-22 ADR-001–ADR-023 accepted. Architecture source: repository files only. No inferred services or undocumented data flows.
Implemented now

Standalone Electron/React/TypeScript Bayes Engine XMLBIF editor only. It is not integrated into INSIGHT.

Accepted target

Single-tenant TypeScript modular monolith: React/Vite, Fastify, internal MCP Gateway, durable jobs, and PostgreSQL in one container.

Research-only boundary

No executable INSIGHT app, patient database, DDI engine, authentication service, plan orchestrator, or unified deployment exists yet.

Persisted Research Case state machine

Exactly one Research Case per Patient. No Encounter, visit, follow-up, or second-case entity.

CPT failure
First generation plus at most two diagnostic retries. No clipping, repair, filling, or renormalization. Third invalid attempt blocks BN output and finalization.
Warning-only outcomes
Completed C-SSRS band and successful DDI findings never block finalization. A failed/unavailable required DDI execution does block.
Deletion branch
Any enabled Psychiatrist may delete immediately: no confirmation, password re-entry, delay, second approval, or Administrator action.

Finalization gate

All conditions are server-side; HTTP success or worker completion alone never proves domain success.

Successful execution linked to the exact final regimen and pinned source.

Successful routed execution when required; accepted snapshot and provenance current.

Plan

Cross-module ruleEach module owns and writes its tables through module services. Cross-module reads use application contracts. Shared transactions are allowed only through an explicit orchestration service.

Logical client, physical executor, internal gateway

Hosted model chooses only among schemas exposed for the current state. Server injects trusted context and executes calls.

Common tool-result boundary

Success: typed data + provenance (toolName, semantic toolVersion, input/output hashes, knowledge versions, execution time) + structured warnings. Failure: typed error code + retryable flag + safe message + optional internal diagnostics.

Raw exceptions, SQL details, absolute paths, credentials, internal UUIDs, names, and official identifiers never enter model-visible results.

Identity invariant
Official identifier tuple (type, issuer, normalized value) is unique. A match opens the existing Patient and atomically overwrites submitted name, birth date, and sex differences with an immutable audit event.
Demographic invariant
Date of birth and MALE | FEMALE are mandatory. Age is derived—today for live profile, Research Case start date for case artifacts. No persisted age snapshot.
Version-pinning invariant
Derived results pin clinical artifact, catalog/rule, DDI source, BN route/model, endpoint/model config, prompt/schema/settings, de-identified input fingerprint, CPT snapshot, and clinician edits.

Persistence, artifacts, backup, restore, deletion

Cross-storage limitations and deletion residue are architectural decisions, not implementation accidents.

Sources: ADR-018–ADR-020, ADR-023
File creationGenerate UUID relative path; write target file first. No staging/atomic rename/content-address rule.
file succeeds
Metadata insertPostgreSQL row stores path, hash, size, owner, access class, lifecycle, provenance.
on read
Authorized verificationBackend resolves relative path and verifies SHA-256; browser never selects arbitrary paths.
Orphan risk
If file succeeds and metadata insert fails—or process crashes—unreferenced file may remain indefinitely. No automatic scanner or cleanup worker.
Backup gap
PostgreSQL dump includes database-held master key and protected data, but excludes every artifact file. Restore expects matching volume to survive independently.
Deletion residue
Patient aggregate and non-audit artifacts are removed, then file deletion gets one best-effort attempt. Complete clinical audit rows and required audit payloads remain.

Deliberately accepted architecture risks

Explicit decisions from the accepted specification; none are “filled in” or softened here.

Source: Deliberately accepted risks

Security, privacy, operations

  • Enabled admin/admin; no forced change.
  • No MFA or SSO.
  • Master key stored with ciphertext.
  • Provider retention/training terms do not gate activation.
  • Any Psychiatrist can immediately hard-delete any shared Patient without confirmation.
  • Audit tables are ordinary mutable PostgreSQL rows.
  • Manual database-only backups; no artifact backup.
  • Best-effort filesystem/database consistency; orphan files possible.
  • Hard deletion preserves complete clinical audit payloads and Patient linkage.

Clinical and model behavior

  • DDI and completed suicide-risk findings are warning-only.
  • AI-imputed details remain hidden; generic notice disappears from final/exported plans.
  • Medication normalization is accepted automatically without clinician confirmation.
  • UNKNOWN medications omit all related DDI pairs but do not block finalization.
  • Structurally passing BN versions activate automatically without clinical approval.
  • LLM regenerates every CPT; software-valid tables are not calibrated clinical probabilities.
  • Patient facts affect inference only through generated CPTs; no evidence clamping.
  • Mutable drafts are last-write-wins; concurrent edits may be silently lost.

Explicitly out of scope

These boxes are architectural absences, not missing diagram nodes.
